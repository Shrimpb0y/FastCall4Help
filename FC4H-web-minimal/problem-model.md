# EVE Online 新手一键求救工具：问题建模

## 1. 目标

为新手玩家提供一个低操作成本的求救工具，优先解决旗舰驾驶员在被敌方抓住时无法快速、准确发出求救信息的问题。工具应尽量自动读取关键状态，生成结构化求救信息，并输出到指定求救渠道。

工具采用三层结构：

1. 输入层：接收求救触发。
2. 逻辑层：判断事件类型，并组装标准化信息。
3. 输出层：把求救信息发送到目标渠道。

## 2. 核心用户

主要用户是 EVE Online 新手玩家，典型特点：

- 不熟悉术语、星系、安全等级、舰船定位。
- 旗舰被敌方抓住时容易慌乱，无法快速描述情况。
- 不知道该向谁求救、该发什么内容。
- AFK 异常提醒暂时保留为未来模式，本阶段不展开。

## 3. 三层结构模型

### 3.1 输入层：双模输入

输入层负责把外部触发转换成统一的内部事件。

#### 模式 A：手动求救

玩家主动点击按钮或使用快捷键触发。

适用场景：

- 旗舰被敌方抓住。
- 旗舰被反跳、被网、被集火。
- 旗舰血量进入危险状态，需要军团或救援频道快速响应。

核心输入字段：

- 求救驾驶员角色名：自动读取，失败时允许手动补填。
- 当前舰船：自动读取，失败时允许手动补填。
- 舰船当前血量状态：自动读取护盾 / 装甲 / 结构的状态，失败时允许手动选择大致状态。
- 当前星系名：自动读取，失败时允许手动补填。
- 敌对人数：后续考虑接入训练过的建议 AI 模型进行自动判断；MVP 可先手动输入或留空。
- 敌对舰船类型：后续考虑接入训练过的建议 AI 模型进行自动判断；MVP 可先手动输入或留空。
- AI 判断接口预留：前置车头、诱导类型、敌方主力是否进场、人工备注。
- 补充说明：可选。

#### 模式 B：AFK 自动求救

AFK 模式暂时跳过，只保留事件类型和未来扩展位置，不进入当前建模细节。

当前约束：

- 不设计 AFK 触发条件。
- 不设计 AFK 监听字段。
- 不设计 AFK 输出策略。
- 后续重新启用时，仍归入 `afk_warning` 事件类型。

### 3.2 逻辑层：事件路由器 + 信息组装器

逻辑层把输入事件转换成可输出的标准求救消息。

#### 事件路由器

事件路由器负责判断“发生了什么”和“应该走哪条处理路径”。

输入：

- 原始事件。
- 当前配置。
- 玩家上下文。
- 冷却状态。

输出：

- 标准化事件。
- 推荐输出渠道。
- 是否需要用户确认。

事件类型建议：

- `manual_distress`：手动求救。
- `afk_warning`：AFK 异常预警。

事件类型只保留以上两种。当前阶段优先建模 `manual_distress`；`afk_warning` 暂时跳过，只保留未来扩展位置。

路由规则示例：

- 手动旗舰被抓求救：输出到游戏聊天 + QQ 群机器人。
- AFK 预警：当前阶段暂不展开。
- 冷却期内重复事件：合并或降噪。

#### 信息组装器

信息组装器负责把结构化事件变成清晰、短小、可行动的求救文本。

消息应包含：

- 求救驾驶员角色名。
- 当前星系名。
- 当前舰船。
- 舰船当前血量状态。
- 敌对人数。
- 敌对舰船类型。
- 原型敌情判断：可能队伍类型、判断信号、置信度。
- 时间戳。
- 可选补充说明。

推荐格式：

```text
[FC4H][紧急]
驾驶员：{character_name}
位置：{system_name}
舰船：{ship_type}
血量：{ship_health}
敌对：{hostile_count} 人，{hostile_ship_types}
判断：{candidate_fleet_types}，置信度：{confidence}
信号：{signals}
备注：{note}
时间：{timestamp}
```

新手友好要求：

- 不要求用户懂复杂术语。
- 每个字段都有默认值。
- 消息短，能直接发进频道。
- 高危场景自动提高醒目程度。

### 3.3 输出层：双模输出

输出层负责把组装好的消息送到目标渠道。

#### 模式 A：游戏内部聊天对话框

目标：

- 让玩家能快速把求救文本发到游戏内频道。

建议实现阶段：

1. MVP：一键复制求救文本到剪贴板，由玩家手动粘贴发送。
2. 增强：打开悬浮窗，显示“复制完成，请粘贴到游戏频道”。
3. 自动化探索：后续单独评估是否允许安全地聚焦聊天框和粘贴。

接口抽象：

```text
GameChatOutput.send(message, options)
```

当前建议语义：

- `send` 不一定等于自动发送。
- MVP 阶段可以表示“复制到剪贴板并提示玩家发送”。

#### 模式 B：QQ 群机器人

目标：

- 将求救消息发到 QQ 群，方便军团、好友或救援群响应。

本阶段只留接口，不实现具体适配。

接口抽象：

```text
QQBotOutput.send(message, options)
```

后续适配可能需要：

- 机器人平台类型。
- 群号。
- 鉴权 token。
- 消息频控。
- 失败重试。
- 敏感信息过滤。

## 4. 领域对象

### PlayerProfile

玩家配置。

字段：

- `characterName`
- `defaultShip`
- `defaultCapitalShip`
- `preferredHelpChannel`
- `qqGroupEnabled`
- `gameChatEnabled`

### DistressEvent

求救事件。

字段：

- `id`
- `source`: 当前阶段主要为 `manual`
- `type`: `manual_distress` / `afk_warning`
- `characterName`
- `systemName`
- `shipType`
- `shipHealth`
- `hostileCount`
- `hostileShipTypes`
- `note`
- `createdAt`

### RoutingDecision

路由决策。

字段：

- `eventId`
- `channels`
- `requiresConfirmation`
- `cooldownApplied`
- `reason`

### DistressMessage

最终消息。

字段：

- `title`
- `body`
- `plainText`
- `metadata`

### OutputResult

输出结果。

字段：

- `channel`
- `success`
- `error`
- `sentAt`

## 5. 状态模型

工具可以用以下状态描述：

- `idle`：待机。
- `manual_collecting`：手动触发后读取求救信息。
- `manual_editing`：自动读取失败或需要补充时，允许用户修正信息。
- `afk_reserved`：AFK 模式保留状态，当前阶段不展开。
- `event_detected`：检测到求救事件。
- `confirming`：等待用户确认。
- `dispatching`：正在输出。
- `cooldown`：冷却中，防止重复求救。
- `error`：输出失败或配置错误。

## 6. 核心流程

### 手动求救流程

1. 用户点击“一键求救”。
2. 输入层尝试自动读取驾驶员角色名、当前舰船、舰船血量状态、当前星系名。
3. 敌对人数和敌对舰船类型先作为可选输入；后续接入训练过的建议 AI 模型进行自动判断。
4. 原型敌情判断器读取前置车头、诱导类型、敌方主力是否进场、备注，并生成简单规则判断。
5. 输入层生成 `manual_distress` 事件。
6. 事件路由器判断输出渠道和冷却状态。
7. 信息组装器生成标准求救文本。
8. 输出层复制到游戏聊天，后续可同时发送 QQ 群机器人。
9. 工具进入冷却状态。

### AFK 自动求救流程

AFK 模式当前阶段暂时跳过，不设计具体流程。

## 7. MVP 边界

第一版建议只做：

- 玩家资料配置。
- 手动旗舰被抓求救按钮。
- 自动读取驾驶员角色名、当前舰船、舰船血量状态、当前星系名的接口位置。
- 敌对人数、敌对舰船类型的手动补充字段或占位字段。
- 前置车头、诱导类型、敌方主力是否进场的 AI 判断接口占位。
- 简单规则判断：黑诱导保留黑隐队 / T3队 / 常规 / 无畏可能；白诱导暂排除 T3队和黑隐队。
- 求救消息模板生成。
- 一键复制到剪贴板。
- QQ 群机器人输出接口占位。
- 简单冷却机制。

暂不做：

- 直接控制游戏客户端发送消息。
- 复杂图像识别。
- 复杂日志解析。
- 训练或接入敌对识别 AI 模型。
- AFK 模式具体实现。
- QQ 机器人真实接入。
- 多角色、多账号管理。

## 8. 关键风险

- 游戏规则风险：自动操作游戏客户端前必须确认边界。
- 信息准确性：星系、舰船、角色名、血量状态如果自动读取失败，必须有可见的修正入口。
- 识别准确性：敌对人数和舰船类型如果由建议 AI 模型判断，必须展示置信度或允许人工确认。
- 隐私风险：QQ 群消息可能泄露位置和角色信息。
- 刷屏风险：机器人和游戏频道都需要频控。

## 9. 下一步设计建议

下一步可以进入产品原型设计：

- 定义主界面。
- 定义手动旗舰被抓求救面板。
- 定义自动读取字段和人工修正字段。
- 定义消息模板。
- 定义输出接口代码结构。

当前输入层最小版本：

- 默认本地只登录一个角色账号。
- 从最新的 `Chatlogs/本地_*.txt` 读取 `Listener` 和最后一次“频道更换为本地”。
- 从最新的 `Gamelogs/*.txt` 作为角色名备用来源。
- 暂不处理多开；后续由输入层或事件路由器按角色会话完善。

后续输入层升级方向：

- 本地日志继续作为低权限、快速定位来源。
- ESI 接口作为主要结构化数据来源。
- 手动输入作为 ESI 无法覆盖或权限不足时的兜底。
- 输入层最终输出仍保持 assembler 当前字段结构，避免逻辑层频繁变化。
- Gamelog 负责识别“被谁反跳/扰断”等被抓事件。
- 预警频道 Chatlog 负责补充敌对人数、舰船类型、队伍信息。
- 事件路由器后续应按时间窗口把 Gamelog 被抓事件和预警频道上报关联。

ESI 适配器预留字段：

- `characterName`
- `characterId`
- `systemName`
- `shipType`
- `location`
- `onlineStatus`
- `shipStatus`
- `source.esi.scopes`

注意：舰船血量、敌对人数、敌对舰船类型未必能直接从 ESI 获得，仍可能需要游戏内视觉识别、玩家手动补充或外部情报源。

预警关联原型：

- 从 Gamelog 匹配类似“XXX 正在尝试跃迁扰断你”的消息。
- 提取 `XXX` 作为攻击者名称。
- 在预警频道 Chatlog 中查找被抓时间点前后数分钟内提到该名称的上报。
- 如果匹配成功，将上报内容作为敌对人数、舰船类型和备注的候选信息。

建议先做一个本地网页或桌面小工具原型，用于验证流程和按钮布局。
